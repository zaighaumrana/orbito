# Client provisioning and Turnstile setup

Status: implemented locally; this follow-up has not been deployed or runtime-tested. The owner reports the earlier control-plane migration, platform-bridge and platform-config are already deployed. Apply this follow-up separately; do not reapply those migrations. No frozen Shop files were changed.

## Once per Platform

1. Review/apply **supabase/migrations/20260926234425_client_provisioning.sql** on Platform. It adds private credential/job records, service-only credential access, operator status/reservation RPCs, audit records and a guard against overlapping configuration/provisioning. Vault must be available; the migration enables it and removes public/anonymous/operator access to the Vault schema, its tables and functions. Private wrappers run with a fixed empty search path. Do not expose platform_private or vault through the Data API.
2. Deploy **platform-provision** and redeploy **platform-config**, including the shared shop-credentials.ts module. Both have verify_jwt=true and also authenticate users in the handler. Keep the existing platform-bridge deployment and verify_jwt=false setting: it uses per-source authentication. Deploy the updated frontend after the migration/functions.
3. Set **PLATFORM_MANAGEMENT_TOKEN** in Platform Edge Function secrets. Give its owner access only to managed Shop projects, with database query read/write and Edge Function secrets write permissions. Management API routes used are POST /v1/projects/{ref}/database/query and POST /v1/projects/{ref}/secrets. The backend uses fixed queries with parameters; browser callers cannot submit SQL, API routes or URLs. Provisioning is restricted to the existing **master_admin** role. Portfolio managers keep module/paper controls; billing people keep finance controls. The management token is never requested by the client form or returned to the browser.
4. Install one Platform polling schedule. Enable pg_cron and pg_net on Platform, then create Vault secrets named **orbito_platform_url** (Platform URL) and **orbito_platform_service_role** (Platform legacy service-role JWT). Run the reviewed **supabase/maintenance/install_platform_bridge_schedule.sql** once on Platform as an administrator. Its named job can be installed again without creating a second same-name schedule for that database user. It calls platform-provision with action=dispatch and the Platform service role. This path rejects ordinary operators and takes no client-selected destination. Do not use a publishable/anon key for this privileged scheduled action.
5. Configure Turnstile as described below. Keep the existing Platform URL/public anon key/auth email frontend settings.

The scheduler selects up to 20 Vault-managed, enabled clients per invocation, oldest attempted poll first, and invokes the finished Shop's existing platform-bridge function in groups of five. Pending provisioning jobs are excluded. Repeated failures do not starve other clients. At one invocation per minute, fleets larger than 20 have a longer poll interval; monitor and size the schedule for the fleet. Inspect cron/pg_net execution results and each client's Last contact. A successful scheduled HTTP request is not proof that every Shop poll succeeded; the response contains per-client success flags. No Shop cron or Shop schema/function deployment is created by onboarding.

Existing clients using PLATFORM_SHOP_CREDENTIALS continue to resolve through that server-secret fallback when no Vault credential exists. Keep their existing scheduling until they are adopted into Vault. Then remove redundant per-Shop schedules after confirming the shared dispatcher works. Apply the migration before redeploying platform-config: resolver errors fail closed rather than silently using stale credentials.

### Turnstile server and frontend configuration

- Enable CAPTCHA protection in **Platform Supabase Auth → Bot and Abuse Protection**, select Cloudflare Turnstile, and save the Turnstile **secret key there**. This is what makes server-side verification authoritative; deploying the frontend alone does not enforce CAPTCHA on direct Auth requests.
- Configure **VITE_TURNSTILE_KEY** with the matching public site key in local .env.local and the Cloudflare frontend build environment. Never put the Turnstile secret key in VITE variables.
- Allow the actual localhost/development hostnames, Cloudflare deployment hostname and production/custom hostname on that widget. No environment bypass or dummy test key is selected by code. Use a permitted localhost hostname for local development, and allow required Turnstile script/frame origins if your deployment uses CSP.
- Add the intended local/deployment/custom-domain /?reset=true redirect URLs to Supabase Auth. Password reset now uses the current origin rather than a hard-coded production domain.

Login renders before session restoration. Login and password-reset requests remain disabled without verification, submit captchaToken to Supabase Auth, and require a fresh challenge after failure. One explicit widget ID and generation guard prevent callbacks from detached screens; cleanup happens before replacing the DOM. Script timeout, offline state and provider errors leave the screen visible with a message and Retry verification. Returning online remounts the widget. Passwords and Turnstile tokens are not persisted by this lifecycle. Offline sign-in is not supported.

## Once per client: Platform UI

1. **Clients → Add Client:** enter business details, Shop project ref, ISO currency and agreed BILL/INVENTORY rates. The new form no longer asks for an anon key. Save opens Client Detail. Registry status Active does not activate the bridge.
2. **Connection / Client Provisioning:** confirm project ref and client binding. Paste the Shop's **legacy service-role JWT** once into the password field. The frozen Shop bridge validates this credential against SUPABASE_SERVICE_ROLE_KEY, so new sb_secret keys are not interchangeable here. The submitted key is checked against the selected project's REST API and its JWT role/ref, cleared from the input immediately, and stored only in Vault. It is never echoed, put into browser storage or embedded into HTML.
3. Select **Provision Client**. Platform discovers the Shop's actual private bridge_config.source_id; validates the contract; creates the unique source mapping; generates a 32-byte random bridge secret; stores its SHA-256 hash for ingestion and its encrypted value in Vault; publishes billing readiness using the existing policy; and sets PLATFORM_BRIDGE_ENDPOINT / PLATFORM_BRIDGE_SOURCE_SECRET on the Shop through Management API. Binding is set only on the matching inactive legacy Shop. Delivery remains disabled, usage mode remains legacy, and the Platform source remains disabled.
4. Configure the existing **Modules / Entitlements** controls: Repairs, Inventory, Technician / Workshop, Live Tracking, EMS, Paper Resupply. Technician uses technician_module_enabled. Paper capability uses the billing projection and never disables printing, thermal ingestion or analytics. Modules are applied through the existing platform-config backend; provisioning does not silently choose commercial entitlements. Use Edit Details / Edit Rates for currency and rates under existing role/history restrictions.
5. Select **Verify Setup**. It checks the stored credential, config readability and service-role table grants, actual source/binding, billing function presence, local source/hash/projection records and the deployed Platform bridge's unauthenticated rejection contract. It reads Shop data without writing test configuration, posting accounting, invoicing or applying a billing revision. “Ready (contract only)” is deliberately not an end-to-end delivery claim. Successful module dispatch and the first live bridge poll establish the remaining runtime behavior.
6. Pause Shop writes, retire cached older clients and reconcile legacy accounting. Enter a cutover note, check the confirmation box and select **Activate Bridge**, then confirm the dialog. Keep writes paused until the operation reports complete. The backend records last_sequence + 1 as a durable plan, then compares the Shop sequence under its row lock while switching usage_mode to bridge. A changed sequence makes that attempt fail safely; after pausing writes, Resume captures a fresh boundary only if Shop still reports legacy mode. It never guesses from a maximum ACK and never releases held_legacy rows.
7. Platform enables the source with that exact cutover and publishes the projection, then enables Shop delivery. The shared Platform schedule includes the client automatically. Resume Shop writes after completion. Confirm Last contact, a new accepted event and the Owner billing view during your manual smoke check.

Provisioning and activation do not invoke the test-accounting reset. The existing guarded reset remains manual and scoped to disposable IDs 1 and 3; it is not a customer cleanup feature.

## Existing clients and credential changes

For an already active client, use **Advanced → Replace Shop Credential** with its existing ref/binding and matching Shop service-role JWT, then Verify Setup. Do not click Provision to recreate its source or change its cutover. Existing source/binding is checked before a credential is replaced. Vault takes precedence after adoption; the legacy JSON secret can remain until all clients are migrated.

**Rotate Bridge Secret** generates one durable new random value per operation. It remembers the prior delivery setting, pauses Shop delivery, updates the Platform hash and Shop Edge secret, then restores the prior delivery setting. In-flight attempts with the old value may fail and retry; immutable event identities prevent duplicate charges. An uncertain operation retains the same secret and request ID on Resume. Rotation never displays either old or new secrets. Replacing a Shop credential stores the supplied replacement; it does not create/revoke Supabase API keys itself.

## Interrupted operations and emergency fallback

One pending provisioning operation per client prevents concurrent provisioning, rotation or configuration dispatch. Request identity, actor, action, non-secret parameters, stage and cutover/rotation plan are durable. Audits include credential storage/replacement, verification, source readiness/activation, completion/failure and module dispatch. Raw secrets and remote error bodies are not logged by these handlers.

- **retry:** refresh status, resolve the displayed cause, then use Advanced → Resume. Re-enter a Shop credential only if the credential-storage stage did not finish. An activation resume requires a fresh pause confirmation. A pre-remote failed attempt (or read-only verification failure) can be dismissed in the UI; its audit remains.
- **running:** another invocation may still be executing. Refresh; do not start a competing operation. If an Edge execution was terminated without saving failure, an administrator must prove it has ended, inspect the Shop bridge_config and the stored Platform job/source, then change that single job to retry via a trusted admin database session, recording an audit entry. There is no automatic lease expiry that allows old operations to race new ones.
- A source that has switched Shop mode but not finished Platform activation must resume the stored cutover plan. Never infer a new boundary from a later last_sequence, rewrite monetary history or release held_legacy events. Do not manually change the Shop bridge_config while this workflow is pending.
- Existing project refs and bindings are immutable through the normal UI. Reassignment, a changed source UUID, unknown config outcomes and historical reconciliation are emergency/admin tasks with read-back and an audit note, not routine onboarding.

If Management API access is unavailable, the UI reports the one-time setup requirement and does not expose generated secrets as a workaround. Existing server-configured clients still use their existing control plane. Enable project access/fix the Platform token, then resume. The earlier implementation report remains the emergency reference for manual source/secret setup and config uncertainty recovery.
