# Verified customer Support v1

Implementation scope: additive Git source only, paired with Orbitoshopv2-v1's customer Support PR. No hosted changes or provider acceptance are implied. Existing Master Open Shop as Support, financial bridge, POS and onboarding contracts remain separate.

## Wire contract

Shop browser calls its own support-tickets function using its public API key and existing user access JWT. Platform is never a browser Supabase client. JSON is streamed with a 16 KiB cap. Unknown fields, arrays and invalid types are rejected before downstream work. Categories: technical, billing_question, account, other. Subject: 1–160 Unicode characters after trimming; message: 1–4000. No attachments or callback URLs.

Create: {action:'create',request_id:UUID,subject,category,message}. List: {action:'list',offset:integer 0..5000}. Get: {action:'get',ticket_id:opaque UUID}. Pages contain at most 50 tickets. Creates return HTTP 202 with accepted, ticket_id and status. List returns tickets, offset, has_more; get returns ticket. A full final page may lead to an empty next page.

Shop adds contract=retrasell-support-v1, project_ref, source_id and client_binding from runtime/live actor context. Its dedicated Support bearer and the transient user access JWT (X-Shop-User-Authorization) go only to the exact configured central HTTPS function. Redirects are errors. Eight-second HTTP deadlines and a 1 MiB response cap bound each call. No refresh token, customer Management token, password or customer service key is forwarded. Do not enable request/header/body capture for these functions in tracing or APM.

Platform first hashes the 256-bit random Support bearer. The registered, enabled, non-revoked credential selects the exact Shop project and explicitly approved public anon JWT. Neither submitted URLs nor JWT issuer claims select a destination. Platform checks asserted project/source/binding, calls that Shop's Auth user endpoint, then invokes support_ticket_actor_context with the real user JWT. Both handlers check Auth user UUID and session_id against the live RPC; no positive authorization cache exists. Tokens require the registered Shop's exact /auth/v1 issuer, authenticated audience, finite unexpired exp, UUID user/session claims, independent Auth signature verification and the live actor RPC. There is no hardcoded maximum remaining lifetime; legitimately configured longer lifetimes are accepted only after those same checks. JWT metadata never grants a role.

The Shop RPC checks confirmed, non-anonymous, non-deleted/non-banned Auth user; existing owned session and not_after; active app_users identity/email; Owner identity shape or matching active Manager employee/email/role; onboarding v2, active local lifecycle and pairing. Cashier, Technician, Orbito Support, unmapped and revoked users fail closed. Central SQL rechecks active client/infrastructure, no outstanding provisioning operation, exact registered source/project/binding and operation-specific scope under the client/credential locks. Reads take client-first FOR SHARE locks, so independent reads coexist; create/enrollment/resolution retain client-first FOR UPDATE. Reads never upgrade locks or perform network calls inside SQL, and authorization is rechecked after waiting.

Authorization across two databases is not globally atomic. SQL accepts a freshly verified actor snapshot for at most 15 seconds (2 seconds future clock allowance), measured after acquiring locks. Revocation immediately after independent verification may race acceptance within that bounded interval. The timestamp is assigned after the live verification response arrives; RPC/network verification time precedes that SQL acceptance window. It is not a strict 15-second global logout deadline. A compromised Shop Auth issuer or central service runtime remains trusted infrastructure, outside the stolen-Support-key-only guarantee. Platform Edge Functions possess privileged project runtime credentials: arbitrary function compromise can invoke service RPCs with fabricated trusted actor snapshots or attack other project surfaces. Dedicated bearer scopes and explicit RPC ACLs restrict ordinary callers; they do not sandbox that privileged runtime.

## Persistence, tenancy and audit

Existing public.support_tickets remains authoritative. Private support_ticket_context stores immutable source/project/binding, namespaced requester/session, original canonical payload/request UUID and opaque ticket UUID. Unique source/request plus the client lock serializes duplicate creates. Identical actor/payload retries return the original receipt before quota consumption; conflicting actor or payload returns 409. New ticket, context, creation event and budget changes commit atomically. Required audit errors roll back acceptance. Default caps are 50 accepted creates/source/hour and 10/actor/hour; rejected operations and accepted retries do not consume new quota. Review these operational limits before activation; stale budget buckets can be pruned by a separately authorized database owner maintenance task.

Owner reads all verified tickets in the current Shop binding; Manager reads only their own. Same Auth user UUIDs in different Shop projects remain distinct. Legacy tickets never appear in customer reads. Customer projections exclude staff identities, raw audits, keys, credential hashes and private metadata. Unknown or inaccessible opaque IDs return the same 404.

Staff page/resolution RPCs recheck canonical live Master/Portfolio Manager authority. Billing gets no Support administration. Staff UI labels records without context **Legacy / Identity Not Verified**; historical matching never creates verified provenance. Atomic resolution requires the expected ticket revision, writes an immutable event and operator audit, and records only an explicit customer-visible response. Equivalent retries produce no extra event. platform_resolve_ticket(integer) remains callable by legitimate existing staff and is an audited compatibility wrapper. Browser raw UPDATE privileges on ticket status/resolved_at are removed so those writes cannot bypass audit.

All new private tables have RLS and explicit raw privilege revocations, including service_role. Narrow service wrappers operate as the migration owner with fixed search_path. Every new helper/wrapper revokes inherited PUBLIC EXECUTE; only intended authenticated or service_role wrappers are granted. Apply migrations as the repository's trusted migration owner (postgres), never a browser role.

## Credential lifecycle and packaging

Only a freshly authenticated canonical Master can call platform-support-enrollment. Its service-only SQL repeats live Master/session validation. Enrollment binds stable request UUID to exact source/project/binding/public key and create/read scopes. Only a currently paired Active v2 Shop without an outstanding provision operation can prepare/install/enable. Status/revocation remain separate; re-pair triggers permanently revoke stale keys. Rotation prepares a new disabled enrollment; enable atomically revokes previous keys. Ticket history remains immutable.

Managed preparation generates independent 32-byte randomness, stores lookup SHA256 in the private table and recovery plaintext only in Supabase Vault. Install sends exactly two new secret names directly to the registered Shop via the existing server PLATFORM_MANAGEMENT_TOKEN. Installation dispatch and acknowledgment have idempotent audit checkpoints. An uncertain install retries the same enrollment/Vault value; no secret response reaches the browser. A successful install alone does not enable anything.

BYO preparation uses locally generated randomness and sends only SHA256 to Platform. Customer Supabase CLI installs secrets using its own account authorization; Platform never collects that account's Management PAT or service key. The owner-operated scripts/support-setup.mjs handles generate/prepare/install/verify/status/revoke with explicit target metadata. No permanent customer Management authority is required.

Verification sends a new challenge to the registered Shop function. A dedicated probe authenticated by the stored key hash checks live local pairing/capability using a service-only RPC and returns an HMAC over contract, challenge, project, source, binding, client and endpoint. The HMAC key is SHA256(installed Support secret); the response never returns that hash. The central handler verifies every field and proof before enable. The hash is sensitive verification material and must stay protected during export/enrollment. A leaked hash can answer a cryptographic challenge, but cannot derive the random bearer or authenticate ticket intake, billing or privileged handoff. The trusted handler only accepts the nonce proof received over HTTPS from the exact registered Shop endpoint; it never accepts caller-provided proof or callback URLs. This verifies the installation's declared secret/pairing, not the integrity of compromised Shop function code. The probe grants no customer ticket authority. Public anon JWT is used only to satisfy the existing Shop gateway contract; actual customer calls still require a real live user session.

The accepted _shared/shop-release.json stays byte-for-byte unchanged. scripts/build-platform-release.mjs --support produces a separate seven-function candidate in supabase/releases/shop-release-support-v1.json. It includes the actor migration and function, with explicit verify_jwt=true. This new candidate normalizes function source line endings to LF for reproducibility across checkouts; default six-function packaging retains its original byte/fingerprint behavior. Do not promote the candidate or rerun completed onboarding to upgrade existing Shops. Optional Support readiness is deliberately absent from the existing mandatory POS/bridge/onboarding preflight. Full activation is gated by independent capability verification and actual user acceptance.

## Anonymous legacy closure

supabase/staged-migrations/close_anonymous_support.sql is **outside active migration discovery**. Current source has no integrated legacy Support sender, but all deployed historical senders have not been verified. Inventory and approve that compatibility decision before creating a new CLI migration containing this closure. It revokes table plus explicit INSERT-column plus sequence grants and removes support_submission; assertions check effective privileges and anonymous policies. Do not claim the vulnerability closed until the owner deploys and verifies it. Never restore anonymous INSERT as routine rollback.

## Error/recovery semantics

400 invalid contract; 401 credential/user authentication failed; 403 live role/pairing/lifecycle denied; 404 generic inaccessible ticket; 409 request/revision conflict; 413 body limit; 429 quota with bounded retry guidance; 503 verification or infrastructure unavailable. Errors are generic and never include raw provider bodies. A timeout may follow a successful commit. Preserve the original request UUID and exact payload and retry; never infer rejection or create a new identity simply because the response was lost. Shop drafts and pending request identities remain memory-only within the current tab/session; closing it loses that local recovery state, so check history before filing a replacement.
